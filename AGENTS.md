# AGENTS.md — agent guide for the Transitrix Studio repository

> This file governs an AI coding assistant working **inside this repository** — Transitrix
> Studio itself (public, MIT, `transitrix/transitrix-studio`), the VS Code extension, CLI,
> and shared diagram renderers. It is intentionally tool-neutral: Claude Code, Cursor,
> GitHub Copilot, Windsurf, or another assistant should all be able to read it directly. If
> you are instead working inside an **adopter's** repository that *uses* Transitrix to model
> an organisation, this is the wrong file — read that repo's own `AGENTS.md` (the shape
> shipped as a template under [`organizations/acme_corp/AGENTS.md`](organizations/acme_corp/AGENTS.md))
> instead.

## 1. What this repo is

Text-first diagram authoring for VS Code and the terminal: structured YAML compiles to BPMN
2.0 XML (and other notation views) with computed layout. See [`README.md`](README.md) for the
product pitch and [`docs/repo-layout.md`](docs/repo-layout.md) for the full directory map.
Notation semantics and design rationale live upstream at
[github.com/transitrix/methodology](https://github.com/transitrix/methodology) — this repo
implements and previews the notations, it does not define them.

- **`src/`** — BPMN compiler + CLI engine (parser, layout, emitter, `transitrix` CLI, `transitrix serve`).
- **`packages/diagrams/`** — `@transitrix/diagrams` workspace: one module per non-BPMN notation.
- **`packages/cli/`** — the slim publishable `@transitrix/cli` bundle.
- **`extension/`** — the VS Code extension; build outputs are gitignored and regenerated by `npm run extension:prep`.
- **`intellij/`** — the companion IntelliJ plugin.
- **`ui/`** — the local browser UI served by `transitrix serve`.
- **`organizations/`** — worked-example organisation repos (e.g. `acme_corp/`) used for hand-testing; not this repo's own code.
- **`tests/`**, **`schemas/`**, **`docs/`** — the Vitest root suite + notation corpus, JSON Schema sources, and adopter/contributor documentation.

## 2. Contribution flow

Full human-facing policy: [`CONTRIBUTING.md`](CONTRIBUTING.md). The agent-relevant summary:

1. Branch from `main`. One concern per pull request — don't bundle unrelated fixes into one
   diff, and don't stack a PR on top of another unmerged one (open PRs merge into `main`
   individually; a PR based on another PR's branch merges into that branch instead, which
   under an auto-merge setup can silently never reach `main`).
2. Open a pull request; do not merge it yourself and do not push directly to `main`. A
   maintainer (human or a narrowly-scoped, published automation grant for small, low-risk
   documentation/chore changes) reviews and merges — treat review as required by default.
3. Never force-push a shared branch, never skip hooks (`--no-verify`), never bypass commit
   signing.
4. If something is ambiguous, resolve it with the maintainer rather than guessing; if you
   must assume undocumented behaviour, spell out the assumption in the PR description.

## 3. Validation before committing

- **After any change that touches compilation or layout** — run `npm test` (runs
  `test:core` under `tests/` and `test:diagrams` under `packages/diagrams/`; see
  [`docs/repo-layout.md`](docs/repo-layout.md) §"Two-suite test strategy" for where a new
  test belongs).
- **New or changed notation examples/fixtures** — must use the canonical
  `*.<notation>.transitrix.yaml` suffix; `npm run check:no-cervin-yaml` fails the build on a
  new `*.cervin.yaml` file (see §5).
- **Extension packaging changes** — `npm run verify-extension-packaging`.
- **Changelog entries** — add a fragment via `node scripts/new-changelog-fragment.mjs Added
  your-change-slug` instead of editing `CHANGELOG.md` directly; see
  [`changelog/fragments/README.md`](changelog/fragments/README.md).

## 4. Design & rendering rules

- **No italic text in any rendered output.** Not in SVG previews, HTML reports, or any UI
  component, in any diagram notation or view. Use weight, size, or colour for hierarchy
  instead.
- **Entity block layout (SVG diagram nodes).** Every entity node shows, top to bottom: name
  (word-wrapped, truncated with `…`; max 2 lines for Goals/FGCA/DGCA, 3 for Nested Blocks),
  entity type (one line, omitted only when the data model carries no type field), entity ID
  (smaller, grey; max 1 line for Goals/FGCA/DGCA, 2 for Nested Blocks). Node size follows the
  shared Size preset (Compact/Normal/Wide; see `ENTITY_NODE_SIZE` in `node-size-presets.ts`).
  Implemented in `render-goals.ts`, `render-fgca.ts`, `render-blocks.ts`.

## 5. Cervin → Transitrix naming

`Cervin` is the pre-rename name; **`Transitrix` is canonical** everywhere (bin, settings,
commands, config, API, docs, examples, new fixtures). Do not add new `cervin`-primary
material. CLI/runtime 2.0.0 removed the bin, `.cervinrc` reader, and default `.cervin.yaml`
acceptance; extension 3.0.0 removed the remaining VS Code shims. New notation files use the
canonical `*.transitrix.yaml` suffixes only.

## 6. What NOT to do

- Do **not** commit a file named `CLAUDE.md` anywhere in this tree — reserved for a private,
  gitignored, maintainer-local coordination file; a CI guard rejects it. This `AGENTS.md` is
  the canonical, committed agent guide for this repository.
- Do **not** run `npm run package-extension` (or any `vsce package` command) unless the
  maintainer explicitly asks for a VSIX build. Make code changes only; packaging is
  triggered on request.
- Do **not** put an archive folder inside `extension/` — `verify-extension-packaging.mjs`
  fails the build if one reappears there. Retired trees move to the repo-root `.archive/`
  (gitignored, never committed) instead of being deleted.
- Do **not** add a new `*.cervin.yaml` fixture or reintroduce a `cervin`-primary identifier
  (see §5).
- Do **not** reference an internal work-item or issue number in committed content (source
  comments, tests, docs, commit messages) — cite the reason, or a decision by name and date,
  instead. This repository is public; a private tracker number is noise to an outside reader.
